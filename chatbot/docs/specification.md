# Техническое задание: HTTP-чат-бот

Статус: требования к реализации на Spring Boot. Программа открывает сеанс общения, сохраняет текстовые сообщения и возвращает их по порядковому номеру. Все внешние операции выполняются по HTTP с JSON. Интеграция с Kernel, его протокол и системные сообщения исключены.

## Архитектура

```text
HTTP-клиент (Postman, веб-интерфейс или Telegram-адаптер)
    → ChatController
    → ChatService
    → SessionRepository

SessionTimeoutManager → ChatService
```

Telegram не обязателен для работы и тестирования. Если подключается Telegram-адаптер, он вызывает тот же HTTP API; доступа к внутренним сервисам или хранилищу у него нет.

Компоненты:

- ChatController: маршрутизация HTTP, валидация DTO и формирование ответов.
- ChatService: открытие и завершение сеансов, сохранение сообщений, получение по номеру.
- SessionRepository / InMemorySessionRepository: хранение и атомарные операции над сеансами.
- SessionTimeoutManager: периодическое удаление просроченных сеансов через @Scheduled.
- Clock: источник времени, заменяемый в тестах.
- ApiExceptionHandler: единый JSON-формат ошибок.

## Модель данных

- ChatSession: sessionId, state, createdAt, lastActivityAt, упорядоченный список сообщений.
- StoredMessage: number, text, receivedAt.
- Состояния: ACTIVE и CLOSED. Закрытые и просроченные сеансы удаляются из хранилища.
- sessionId — случайный непрогнозируемый идентификатор, выдаваемый сервером. В учебном API он даёт доступ к сеансу и не должен попадать в публичные журналы.

## HTTP API

| Метод и путь | Вход | Успешный ответ |
| --- | --- | --- |
| POST /api/sessions | Без тела | 201: sessionId, createdAt, expiresAt; Location на созданный сеанс |
| GET /api/sessions/{sessionId} | Идентификатор | 200: состояние, количество сообщений, expiresAt |
| POST /api/sessions/{sessionId}/messages | {"text":"Привет"} | 201: number, text, receivedAt; Location на сообщение |
| GET /api/sessions/{sessionId}/messages/{number} | Номер начиная с 1 | 200: number, text, receivedAt |
| DELETE /api/sessions/{sessionId} | Идентификатор | 204 без тела |

Создание сеанса соответствует Login, получение сообщения — Remember, удаление сеанса — Logout. Каждое создание открывает новый независимый сеанс. Повторное удаление возвращает 204. Все остальные операции с отсутствующим, закрытым или просроченным сеансом возвращают 404.

Ошибки: 400 — неверный формат запроса, пустой текст, превышение длины или неположительный номер; 404 — сеанс или сообщение не найдено; 409 — достигнут лимит сообщений в сеансе; 415 — неподдерживаемый Content-Type при отправке тела.

Формат ошибки:

```json
{"code":"MESSAGE_NOT_FOUND","message":"Сообщение с указанным номером не найдено"}
```

## Правила работы

1. Сохраняются только текстовые сообщения; исходный текст возвращается без изменения.
2. Нумерация начинается с 1, непрерывна внутри сеанса и не зависит от других сеансов.
3. Пустой или состоящий только из пробелов текст отклоняется.
4. Тайм-аут по умолчанию — 15 минут без активности; настраивается в конфигурации.
5. Успешная запись или получение сообщения обновляет lastActivityAt. Чтение статуса и ошибочные запросы активность не продлевают.
6. При now >= lastActivityAt + timeout сеанс считается истёкшим. Это проверяется при каждом запросе, независимо от фоновой очистки.
7. После завершения сеанса история удаляется. Данные первой версии хранятся в памяти и теряются при перезапуске.
8. Начальные ограничения: 1000 сообщений на сеанс и 4096 Unicode-кодовых точек на сообщение; значения настраиваются.
9. Проверка срока, изменение истории и закрытие одного сеанса выполняются атомарно. Между независимыми сеансами допускается параллельная обработка.
10. Каждый принятый POST сообщения создаёт новую запись. Автоматический повтор POST после неопределённого сетевого результата может создать дубликат; гарантия идемпотентности в первой версии не заявляется.

## Жизненный цикл приложения

Приложение запускается и останавливается стандартными средствами Spring Boot. При остановке прекращаются фоновые задачи. HTTP-команды для завершения процесса не нужны. Тайм-ауты реализуются приложением, без внешних системных сообщений.

## Проверки и критерии приёмки

- Создание сеанса и сохранение нескольких сообщений.
- Получение точной копии текста по номеру.
- Ошибки формата, неизвестный сеанс и отсутствующий номер.
- Изоляция истории разных сеансов.
- Закрытие, повторное закрытие и обращение после закрытия.
- Истечение срока точно на границе; отсутствие продления ошибочными запросами.
- Лимиты длины текста и количества сообщений.
- Конкурентные записи не получают одинаковые номера и не теряются.
- Одновременные закрытие и запись не восстанавливают удалённый сеанс.
- Юнит-тесты JUnit 5/Mockito, HTTP-тесты Spring MVC и коллекция Postman.
- JaCoCo: покрытие строк, методов и ветвей не менее 80%.
