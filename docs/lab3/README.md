# Лабораторная работа № 3. Разработка тестов

## Цель
Разработать рабочую тестовую документацию для приложений Chatbot и Hotel.
Форма документации — Test Cases. Swagger UI используется как интерфейс отправки API-запросов.
Проверки Swagger относятся к интерфейсу документации API; отдельного пользовательского GUI у приложений нет.

## Объекты и окружение
- Приложения: Chatbot и Hotel, версия 0.0.1-SNAPSHOT.
- Точная сборка: перед прогоном записать вывод `git rev-parse HEAD`.
- Ф. И. О. тестировщика: заполнить перед прогоном.
- Период тестирования: заполнить реальные даты начала и окончания.
- ОС, браузер и версии: заполнить по фактическому окружению.
- JDK: 21; Maven Wrapper из репозитория.
- Активность: функциональное тестирование API, граничные и негативные проверки; проверки Swagger UI.
- Начальные данные Hotel: 25 свободных номеров из data.sql: 1–10 ECONOMY/200,
  11–20 STANDARD/400, 21–25 PREMIUM/600. Перед независимым прогоном перезапустить Hotel.
- Chatbot: по умолчанию 15m неактивности, 1000 сообщений, 4096 кодовых точек Unicode.
  Сеансы и сообщения исчезают после перезапуска.

## Запуск в PowerShell из корня репозитория
```powershell
.\mvnw.cmd clean verify
.\mvnw.cmd -pl chatbot spring-boot:run
# В другом терминале:
.\mvnw.cmd -pl hotel spring-boot:run "-Dspring-boot.run.arguments=--server.port=8081"
```

| Приложение | Swagger UI | OpenAPI JSON |
| --- | --- | --- |
| Chatbot | http://localhost:8080/swagger-ui.html | http://localhost:8080/v3/api-docs |
| Hotel | http://localhost:8081/swagger-ui.html | http://localhost:8081/v3/api-docs |

На Linux/macOS используйте `./mvnw`. В Swagger раскройте операцию, нажмите **Try it out**,
заполните параметры/JSON и нажмите **Execute**. Сверяйте **Server response**, а не только
пример в разделе Responses. UUID копируется из ответа создания сеанса.

## Требования и модули
| ID | Модуль / подмодуль | Требование |
| --- | --- | --- |
| C-01 | Сеансы / создание и состояние | POST создаёт независимый ACTIVE-сеанс с UUID, messageCount=0, createdAt и expiresAt; GET возвращает состояние |
| C-02 | Сообщения / запись и чтение | POST сохраняет текст без изменения, возвращает номер с 1; GET возвращает текст, номер и receivedAt; успешные запись/чтение продлевают неактивность |
| C-03 | Сообщения / ограничения | Пустой/blank/null/отсутствующий текст и длина сверх лимита дают 400; превышение количества — 409 |
| C-04 | Сеансы / завершение и срок | DELETE идемпотентен (204); закрытый/истёкший сеанс недоступен (404); GET состояния не продлевает срок |
| C-05 | Ошибки API | Неверный UUID/номер/JSON — 400; неизвестный сеанс/сообщение — 404; формат тела кроме JSON — 415; ошибка имеет code и message |
| H-01 | Поиск / бюджет | GET /bookings?money возвращает только свободные номера с price <= money, отсортированные по цене |
| H-02 | Поиск / результат | 200 и массив объектов number, price, roomCategory; при отсутствии результатов — 404 и message «Таких номеров нет» |
| H-03 | Поиск / ввод и методы | money обязателен, тип int; отсутствующее/неразбираемое значение — 400; POST /bookings — 405 |
| H-04 | Поиск / отсутствие изменений | Поиск не занимает комнату, не списывает деньги, не сохраняет клиента |
| UI-01 | Swagger / отображение | Загружается Swagger каждого приложения, доступны операции, параметры, примеры и ответы |
| G-01 | General / выполнение | Swagger позволяет отправлять независимые запросы и показывает фактический URL, статус, заголовки и тело |

## Изменённые настройки для специальных кейсов Chatbot
Остановить обычный экземпляр Chatbot, затем запустить отдельный экземпляр с нужным аргументом:
```powershell
# CHAT-011
.\mvnw.cmd -pl chatbot spring-boot:run "-Dspring-boot.run.arguments=--chatbot.session-timeout=3s"
# CHAT-012
.\mvnw.cmd -pl chatbot spring-boot:run "-Dspring-boot.run.arguments=--chatbot.session-timeout=30s"
# CHAT-013
.\mvnw.cmd -pl chatbot spring-boot:run "-Dspring-boot.run.arguments=--chatbot.max-messages=2"
```
После специального кейса остановить процесс и вернуть обычный запуск. Создавать новый UUID
после каждого перезапуска. Настройки одного специального кейса не переносить в другой.

## Документы и порядок работы
1. Выполнить общие [тест-кейсы Swagger](swagger-test-cases.md) отдельно для каждого приложения.
2. Выполнить [тест-кейсы Chatbot](chatbot-test-cases.md) и [Hotel](hotel-test-cases.md).
3. Smoke — базовый рабочий маршрут; MAT — основные функции и границы; AT — расширенные негативные и специальные сценарии.
   Эти метки задают глубину функциональных проверок, а не процент покрытия JaCoCo.
4. Каждый кейс изолирован, если в предусловиях явно не сказано иначе. Подготовка через API также выполняется в Swagger.
5. Для параметризованного кейса проверить каждое указанное значение отдельно; записать результат каждого набора.
6. Для каждого ID заполнить [журнал](execution-log.md). Не ставить Passed без реального выполнения.
7. Сохранить скриншоты существенных ответов: ID кейса, запрос, Server response. Для автоматических тестов — вывод Maven.

Swagger может отклонять некорректные параметры до отправки запроса. В этом случае проверка HTTP-ошибки
выполняется через PowerShell/curl (инструкция в кейсе), а блокировка Swagger фиксируется отдельно.
Нельзя записывать ответ клиента как ответ сервера.

## Выводы
Подготовлены требования и тест-кейсы для двух API, включая общие проверки Swagger,
позитивные маршруты, границы и ошибки. Итог о качестве конкретной сборки формулируется
после прогона по журналу; наличие документации не означает успешное выполнение проверок.
